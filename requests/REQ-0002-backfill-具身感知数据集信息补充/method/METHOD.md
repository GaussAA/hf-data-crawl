# 过程记录：REQ-0002 具身感知数据集信息补充

这份需求交付的是「补全后的表」。表里每一格要么有底库来源，要么有判读依据，
两者都在本目录里。方法是：**机械的交给引擎，判断的交给判读表，判读表本身可复验。**

## 目标

把对方给的 40 列空表（只有 E 列 URL 有值）按约定口径填满，交回同一张表。
做完的标准：

- 声明过的 21 列，机械列全部由引擎填入，人判列全部有值或有明确留空理由；
- 对方原始表一字未改（`input/` 里是受理时的快照）；
- 每一格能回答来源（底库某列 / README 原文 / 无客观来源）。

## 步骤

1. **受理**：`huggingface.co/datasets/...` 链接清单复制进 `input/`，此后不再读外部文件。
   表结构是第 1 行阶段分组、第 2 行列名，标识列 `URL`。
2. **逐列分类**（一次性判断，写进 `spec.yaml` 的 `fill.columns`，共 21 列）：
   - `field` 11 列 —— 底库有直接对应的列（名称、作者、简介、时间、大小、下载量、模态、语种、技术方向……）；
   - `template` 1 列 —— 论文 URL 按 `arxiv_ids` 拼；
   - `const` 1 列 —— 来源固定 HuggingFace；
   - `manual` 8 列 —— 底库没有、或不可信，须读 README / splits 判定。
3. **预演**：`request run REQ-0002 --dry-run`，看逐列覆盖多少格。覆盖率不对说明分类错了，
   回到第 2 步，别急着往下走。
4. **人工判读**：逐库读 README 原文与 datasets-server 的 splits，按下面「判据」逐列判，
   结论写进 `overrides.json`（键为 `作者/名称`）。
5. **自检**：`python method/scripts/verify_overrides.py` —— 查判读表有没有错位。
6. **交付**：`request run REQ-0002`。产物只落 `deliveries/<时刻>/`。

## 机器算的 / 人判的

| 环节 | 谁做 | 判据 |
| --- | --- | --- |
| 名称、作者、时间、下载量、点赞、大小 | 引擎 | 底库同名列直接取；大小按十进制折 GB |
| 模态、语种、技术方向 | 引擎 | 底库列表列，按 `、` 连接并译成页面写法 |
| 论文 URL | 引擎 | `arxiv_ids` 首项拼 `arxiv.org/abs/`；没登记则整格留空，不拼半截链接 |
| 是否包含 README | 人 | 仓库文件清单里有没有 README.md（底库该列只对头部一万条抓过） |
| 数据量级（条） | 人 | README 自述的实例数并注明单位；单位不统一，机械折不出可比数字 |
| 训练阶段 | 人 | README **明写** pretrain / fine-tune / post-training 才算；含糊的不猜 |
| 数据构成 | 人 | 概括 README 里的数据组织方式（按任务/按本体/多源） |
| 是否为答题 | 人 | 数据形态是不是问答对 |
| 是否为 benchmark | 人 | README 或论文标题是否自称 benchmark；不按「像评测集」推断 |
| 是否有测试集 | 人 | datasets-server 的 splits 里有没有 test 划分 |
| 构造方式 | 人 | 仿真合成 / 真机遥操作 / 多源整理，三者之一 |

**机械列也可以被人判结果覆盖**：`简介`、`技术方向`、`数据模态`、`论文 URL`、
`数据大小(GB)` 五列有若干格改用了判读值——因为引擎在这些列上取的是 README 首段
机器摘要、task_categories 机器码或未登记的 arxiv 号，不如人读一遍准。覆盖了多少格，
`verify_overrides.py` 每次都会报出来。

## 脚本

| 脚本 | 干什么 | 怎么跑 |
| --- | --- | --- |
| `method/scripts/verify_overrides.py` | 判读表自检：URL 是否在清单里、列名是否声明过、人判列有没有空值、哪些机械列被人工改判 | `.venv/Scripts/python.exe requests/<本目录>/method/scripts/verify_overrides.py` |

**当时那次判读没有留下脚本。** 16 份 README 是逐份读、逐条判的，在会话里一次性完成，
没有沉淀成可重跑的东西——这正是本需求当初缺的那一环。上面这份自检脚本是后来补的，
它验的是「结论表有没有错位」，不是「当时的判断对不对」。这一点写在这里，不假装它存在。

## 环境

- 底库：`data/exports/datasets.parquet`；本次基于哪一版，见 `deliveries/20261108T180736/manifest.json` 的 `source.current_md5`
- 代码：`hf-data-crawl` 版本与提交号，见同份 manifest 的 `method.env`
- 依赖：`openpyxl`（读表）、`pyyaml`（读口径）、`hf_data_crawl.delivery.backfill.parse_reference`（URL 归一，复用引擎而不另写正则）

## 已知边界

- **README 会变**。判读基于抓取当时那一版 README，HF 上改了就无法逐字复现同一判断；
  复现的是「按同一判据重新判一遍」这件事，不是逐字相同的结论。
- **单位不统一**。「数据量级(条)」把轨迹、回合、问答对、小时混在一列，只能逐格注明单位，
  不能横向比较。
- **14 列内部流程列**（筛选是否可用、存储路径、处理人、质检结果等）与**3 列无客观来源的列**
  （是否关联榜单、是否有测试结果、质量评估分）留空是口径，不是遗漏。
- **未命中底库的行整行留空**。本单 16 行全部命中；若将来对方表里出现底库没有的库，
  报告会在 `manifest.fill.missing_ids` 里点名，不会静默留白。
