# 过程记录：REQ-0004 开源query轨迹数据集P1清单字段拼接

对方给了一张 28 行、只有三列（序号 / 名称 / URL）的表，一句话要求：**把所有能拿到的
字段都拼接进这张表里**。这份记录要回答两件事：拼了哪些、为什么只有这些；以及
「换个人照着做，能不能拿到同一份表」。

**v3 起多了一层**：这 28 条是长尾，原先不在任何「按下载量取头部」的采集批次里，
`card_*` / `server_*` / `files_*` 全空。对方明确同意「这批只有 28 条，破例允许直接
从上游爬」，于是按名单补采了一次，把**实测行数**这类原本没有的字段补出来。补的是
底库，交付仍只读底库——两者的先后顺序不能倒。

## 需求成立性

> 2026-11-18 补记（这次受理的原始对话还在，下面写的是当时的判断）。

**对方说的做法**：把 28 条候选的「所有能拿到的字段」拼进原表。

**他要的结果**：P1 立项评估用的候选清单——一眼看出规模、活跃度、许可与任务类别。

**照字面做的风险**：「所有字段」是个开放集合。底库里没有的（实测行数、文件数、大小）
只能爬上游；没有客观来源的（训练阶段、部分许可证细节）只能人判或留空。照字面「全填上」，
表会看起来完整、实际把猜测当成了事实。

**结论**：需求成立。口径把「所有能拿到的」落实成**底库 ∪ 按名单补采**（v3 的 16 列），
没有来源的列留空并写理由；「上游补采」这件事在受理时才定下来，也没有写进初版口径——
那是这条需求里最值得记住的一次返工。

## 目标

把底库里这 28 个数据集能拿到的元信息，按约定口径拼到对方原表的最右侧，交回**同一张表**。

做完的标准：

- 原表三列（序号 / 名称 / URL）一格未改；
- 追加的 39 列由引擎填，且**每一列都真有值**（整列为空的列不进表，见下面「判据」）；
- 上游补采只补这 28 个库，不籍此把全站扫一遍；
- 拿不到的（上游返回「不支持」、卡片本来就没写的）在交付 README 里点名，不说成「没有」；
- 产物与档案能自证：输入快照 sha256、底库指纹、逐列写入格数。

## 步骤

1. **受理**：`hf-data-crawl request new REQ-0004 --kind backfill --source <原表>`，
   原件被复制进 `input/`（此后不再读 Downloads，原件也绝不被改动）。
2. **摸清表的形状**：`Sheet1`，第 1 行就是列名（`序号 / 名称 / URL`），28 条数据从第 2 行起，
   标识列取 `URL`（`名称` 是对方手填的，只用来事后核对，不作为解析依据）。
3. **按名单补采**（v3 起；只在对方允许爬上游时做）：
   ```bash
   hf-data-crawl enrich       --ids <28 个 id，逗号分隔>
   hf-data-crawl fetch-sizes  --ids <同上>
   hf-data-crawl fetch-files  --ids <同上>            # 有的库文件树超一页
   hf-data-crawl fetch-files  --ids <截断的那几个> --max-pages 200 --refresh-truncated
   hf-data-crawl fetch-readme --ids <同上>
   ```
   `--ids` 在四条命令上是同一套语义：**名单即范围，`--top` 不参与截断**；一个都没匹配上
   直接报错，不让「跑完 0 行、状态 success」冒充正常。`fetch-files` 默认只取一页，
   取不完会标 `truncated`——它是「清单没取全」的凭据，不是失败。
4. **定收录规则**：底库 `datasets` 视图 74 列先分四桶（A 原表已有 / B 平台与管道记账 /
   C 这批整列为空 / D 其余），D 桶全拼，其余各有理由不拼；D 桶里有三列破例不拼
   （JSON 明细 + 两列与已拼列逐行同值），理由与「同值」的复核都在脚本里。
   分桶由 `method/scripts/columns.py` 现算并核对 spec —— 手抄的列清单会随底库加列而过期。
5. **写口径**：`spec.yaml` 的 `fill.columns` 39 条，全部 `append: true`
   （原表没有这些列，引擎据此追加到最右侧，见 GLOSSARY #100）。
6. **预演**：`hf-data-crawl request run REQ-0004 --dry-run`，逐列看覆盖。
   `语种 13/28`、`arXiv编号 11/28` 是底库本来就缺，不是解析失败；
   `实测行数 27/28` 缺的那一个，是上游 datasets-server 返回「不支持」。
7. **交付**：`hf-data-crawl request run REQ-0004`，产物只落 `deliveries/<时刻>/`。
8. **自检**：`method/scripts/verify_table.py deliveries/<时刻>` —— 原表三列未改、
   追加列顺序与 spec 一致、每列都真有值、manifest 的 `appended` 与输入表头分得清。

## 机器算的 / 人判的

| 环节 | 谁做 | 判据 |
| --- | --- | --- |
| 原表三列 | 不碰 | spec 不声明它们；引擎只写声明过的列 |
| 卡片、规模、文件清单、README | 采集层 | 一律走上游官方接口（`enrich` / `fetch-sizes` / `fetch-files` / `fetch-readme`），写进底库再读；不手抄网页、不猜数字 |
| 作者、展示名、时间、sha、下载量、点赞、趋势分、三列大小、访问门槛、许可 | 引擎 | 底库同名列直接取；大小按十进制折 GB；时间取日期 |
| 实测行数/列数、配置数、文件数、文件格式分布、是否有README | 引擎 | datasets-server 与 tree 接口的**实测值**，与作者声明值分开成列，不取平均也不互相顶替 |
| 简介 | 引擎 | `description` 做 prose 压平（去 HTML 残片、并空白），不改写措辞 |
| 任务类别、模态、语种、格式、适配库、规模档、标签、自定义标签、地区、arXiv | 引擎 | 底库列表列按 `、` 连接；任务类别/模态/访问门槛/布尔列按词表译成中文 |
| 作者声明…（四项） | 引擎 | 卡片 YAML 里作者自己写的值，原样取；与平台归一值不一致时**不改**，让两列并排说话 |
| 论文URL | 引擎 | `arxiv_ids` 首项拼 `arxiv.org/abs/`；没登记则整格留空，不拼半截链接 |
| 收哪些列 | 人（一次性，可复算） | 四桶划分 + D 桶里三列破例；由 `columns.py` 现算并核对 |
| 名称与 URL 是否一致 | 脚本 | 逐行 `parse_reference(URL) == 名称`，不一致点名（判定为对方表错位，不是本单能修的） |

**本单没有人工判读列**：对方要的是「能拿到的字段」，判读题（训练阶段、数据构成、
是否 benchmark）不在这次口径里；底库没有的值留空，不拿近似值顶替。

## 脚本

| 脚本 | 干什么 | 怎么跑 |
| --- | --- | --- |
| `method/scripts/columns.py` | 把底库 74 列分四桶，复核 D 桶里三列「与已拼列同值」的说法，并核对 spec 声明的底库列正好是 D 桶减去这三列；不一致退出码 1 | `.venv/Scripts/python.exe requests/<本目录>/method/scripts/columns.py` |
| `method/scripts/verify_table.py` | 交付前查输入（表头/序号连续/名称与 URL 一致），交付后查产物与档案（原表未改、追加列齐全且逐列有值） | 同上，末尾加 `deliveries/<时刻>` |

改脚本后要跑 `hf-data-crawl request method REQ-0004` 重算指纹，否则交付会被拦下。

## 环境

- 底库：`data/`（Gold `datasets` 视图；本次基于哪一版见 `deliveries/<时刻>/manifest.json` 的 `source.current_md5`）
- 代码：`hf-data-crawl` 版本与提交号，见同份 manifest 的 `method.env`
- 依赖：`openpyxl`（读表写表）、`polars`（读视图）、本仓 `hf_data_crawl.delivery` 与 `hf_data_crawl.acquire`

## 变更记录

- **v1（2026-11-17）**：首版。为「把能拿到的字段拼进来」给回填引擎加了追加列能力
  （`append: true`，GLOSSARY #100）——此前列名对不上表头一律报错，只有两条歪路：
  把新列名先写进输入表（等于改了原表快照），或绕过 `fill:` 规则手工补。
- **v2（2026-11-17）**：给发布时间、更新时间、近30天下载量、累计下载量、点赞量、趋势分、
  访问门槛、数据大小八列补了列宽。为什么换：v1 产物里日期与数字落在 Excel 默认的 8.43 字宽列，
  日期是文本，被右邻格挤得只剩半截——值填对了、眼睛看不见，等于没填。
  **这一版只动显示宽度，不动取值口径**：`request compare` 两版逐格比，改值格数应为 0。
- **v3（2026-11-17，对方明确允许这批爬上游）**：按名单补采这 28 个库的卡片、规模、
  文件清单与 README（`enrich/fetch-sizes/fetch-files/fetch-readme --ids`，四条命令都补了
  `--ids`，此前只有 enrich 与 fetch-readme 支持点名），新增 16 列，其中
  **实测行数 / 实测列数 / 配置数 / parquet大小 / 内存占用 / 文件数 / 文件格式分布 /
  是否有README / 展示名 / 许可证名称 / 作者声明四项** 都是 v2 里整列为空、这次才有的。
  为什么必须补：这 28 条是按下载量取头部的长尾，头部采集永远轮不到它们，而「多少行、
  多大、几个文件」正是评估数据集最先要看的数。补采只针对这 28 个库，全站覆盖不受影响。
- **v3 附（2026-11-17，纯格式）**：`method/scripts/` 两个脚本按仓库的 `ruff format`
  重排了换行与缩进——此前它们不合格，`uv run ruff format --check .` 在合并后是红的。
  **逻辑一字未改**（`ast.parse` 通过、四桶与自检行为不变），指纹已随本次重算。
  为什么不豁免这两个文件：仓库规定 ruff 覆盖全仓（`tests/test_ci_config.py` 钉着），
  给交付脚本开豁免会变成每份需求都要开一次的先例；而 `request method` 重算指纹本来
  就是「改过脚本」的标准动作。

## 已知边界

- **补采是一次性的**。全局的 `card_*` / `server_*` / `files_*` 仍只覆盖头部（卡片 0.2%、
  文件清单只有本单这 28 行），别把这份表的完整度当成全站数据质量。
- **一个库的实测行数为空**：`GML-FMGroup/CanvasCraftSFT` 上游 datasets-server 返回
  「不支持」（`status=unavailable`），不是没抓。同理，2 个库的 `server_num_bytes_*` 为空。
- **一个库的文件树没取完**：`ChrisDing1105/unified-agent-trajectories` 单库超过 20 万条
  （本次取 200 页），`文件数` 17.1 万是**下限**，标了 `truncated`；仓库总字节以
  `数据大小(GB)`（仓库元数据）为准，不受此限。
- **数值是交付那一刻的快照**。下载量、点赞、趋势分每天在变；实测行数也会随作者改数据变。
  同一版底库 + 同一份输入重跑逐字节一致，跨日重跑不会一致——`manifest.source.current_md5`
  是分清这两件事的唯一凭据。
- **简介会被 HF 截断**（末尾附「见数据集页」），不是全文；README 全文已在底库 `readme` 表里
  （23 个库本来就有、5 个本单补的），但它是每行数 KB 的长文本，**不进宽表也不进交付**，
  要读去底库查。
- **原件在受理后被 Excel 另存过一次**（2026-11-17 17:27 前后，`Downloads` 里的那份从
  10,303 字节涨到 13,044 字节）。已于同日逐格复核：29 行 × 3 列**一格未变**，只是样式与
  文档属性被重写。`input/` 里保留的仍是受理那一刻的快照（sha256 `f522886a…`），档案里的
  指纹说的是它；将来若有人拿 Downloads 里的原件去比 sha256，会不相等——原因就是这个，
  不是我们改过表。
- **对方表若加列**（处理人、质检结果这类内部流程列），本份 spec 不声明、引擎不碰；
  若对方把某列改名成与我们追加列同名，交付会因「表里已有该列」走填充而非追加，
  届时按新表重新升版。
