# 过程记录：REQ-0004 开源query轨迹数据集P1清单字段拼接

对方给了一张 28 行、只有三列（序号 / 名称 / URL）的表，一句话要求：**把所有能拿到的
字段都拼接进这张表里**。这份记录要回答两件事：拼了哪些、为什么只有这些；以及
「换个人照着做，能不能拿到同一份表」。

## 目标

把底库里这 28 个数据集能拿到的元信息，按约定口径拼到对方原表的最右侧，交回**同一张表**。

做完的标准：

- 原表三列（序号 / 名称 / URL）一格未改；
- 追加的 23 列由引擎填，且**每一列都真有值**（整列为空的列不进表，见下面「判据」）；
- 拿不到的（未抓过的卡片字段、未采集的规模与文件清单）在交付 README 里点名，不说成「没有」；
- 产物与档案能自证：输入快照 sha256、底库指纹、逐列写入格数。

## 步骤

1. **受理**：`hf-data-crawl request new REQ-0004 --kind backfill --source <原表>`，
   原件被复制进 `input/`（此后不再读 Downloads，原件也绝不被改动）。
2. **摸清表的形状**：`Sheet1`，第 1 行就是列名（`序号 / 名称 / URL`），28 条数据从第 2 行起，
   标识列取 `URL`（`名称` 是对方手填的，只用来事后核对，不作为解析依据）。
3. **定收录规则**：底库 `datasets` 视图 74 列先分四桶（A 原表已有 / B 平台与管道记账 /
   C 这批整列为空 / D 其余），D 桶全拼，其余各有理由不拼。分桶由
   `method/scripts/columns.py` 现算并核对 spec —— 手抄的列清单会随底库加列而悄悄过期。
4. **写口径**：`spec.yaml` 的 `fill.columns` 23 条，全部 `append: true`
   （原表没有这些列，引擎据此追加到最右侧，见 GLOSSARY #100）。
5. **预演**：`hf-data-crawl request run REQ-0004 --dry-run` → 28 行、写入 564 格、
   空 80 格；逐列看覆盖，`语种 13/28`、`arXiv编号 11/28` 都是底库本来就缺，不是解析失败。
6. **交付**：`hf-data-crawl request run REQ-0004`，产物只落 `deliveries/<时刻>/`。
7. **自检**：`method/scripts/verify_table.py deliveries/<时刻>` —— 原表三列未改、
   追加列顺序与 spec 一致、每列都真有值、manifest 的 `appended` 与输入表头分得清。

## 机器算的 / 人判的

| 环节 | 谁做 | 判据 |
| --- | --- | --- |
| 原表三列 | 不碰 | spec 不声明它们；引擎只写声明过的列 |
| 作者、时间、sha、下载量、点赞、趋势分、大小、访问门槛 | 引擎 | 底库同名列直接取；大小按十进制折 GB；时间取日期 |
| 简介 | 引擎 | `description` 做 prose 压平（去 HTML 残片、并空白），不改写措辞 |
| 任务类别、模态、语种、格式、适配库、规模档、许可证、标签、自定义标签、地区、arXiv | 引擎 | 底库列表列按 `、` 连接；任务类别与模态、访问门槛按词表译成中文 |
| 论文URL | 引擎 | `arxiv_ids` 首项拼 `arxiv.org/abs/`；没登记则整格留空，不拼半截链接 |
| 收哪些列 | 人（一次性，可复算） | 四桶划分：A 原表已有、B 平台与管道记账、C 整列为空，D 全拼；由 `columns.py` 现算并核对 |
| 名称与 URL 是否一致 | 脚本 | 逐行 `parse_reference(URL) == 名称`，不一致点名（判定为对方表错位，不是本单能修的） |

**本单没有人工判读列**：对方要的是「能拿到的字段」，判读题（训练阶段、数据构成、
是否 benchmark）不在这次口径里；底库没有的值留空，不拿近似值顶替。

## 脚本

| 脚本 | 干什么 | 怎么跑 |
| --- | --- | --- |
| `method/scripts/columns.py` | 把底库 74 列分四桶，并核对 spec 声明的底库列正好是 D 桶；不一致退出码 1 | `.venv/Scripts/python.exe requests/<本目录>/method/scripts/columns.py` |
| `method/scripts/verify_table.py` | 交付前查输入（表头/序号连续/名称与 URL 一致），交付后查产物与档案（原表未改、追加列齐全且逐列有值） | 同上，末尾加 `deliveries/<时刻>` |

改脚本后要跑 `hf-data-crawl request method REQ-0004` 重算指纹，否则交付会被拦下。

## 环境

- 底库：`data/`（Gold `datasets` 视图；本次基于哪一版见 `deliveries/<时刻>/manifest.json` 的 `source.current_md5`）
- 代码：`hf-data-crawl` 版本与提交号，见同份 manifest 的 `method.env`
- 依赖：`openpyxl`（读表写表）、`polars`（读视图）、本仓 `hf_data_crawl.delivery`

## 变更记录

- **v1（2026-11-17）**：首版。为「把能拿到的字段拼进来」给回填引擎加了追加列能力
  （`append: true`，GLOSSARY #100）——此前列名对不上表头一律报错，只有两条歪路：
  把新列名先写进输入表（等于改了原表快照），或绕过 `fill:` 规则手工补。
- **v2（2026-11-17）**：给发布时间、更新时间、近30天下载量、累计下载量、点赞量、趋势分、
  访问门槛、数据大小八列补了列宽。为什么换：v1 产物里日期与数字落在 Excel 默认的 8.43 字宽列，
  日期是文本，被右邻格挤得只剩半截——值填对了、眼睛看不见，等于没填。
  **这一版只动显示宽度，不动取值口径**：`request compare` 两版逐格比，改值格数应为 0。

## 已知边界

- **底库只对头部补过卡片**。这 28 个库都没有 `card_*`（展示名、config 数、作者声明的行数）
  与 `server_*`（datasets-server 实测行数、字节）、`files_*`（文件清单、是否有 README）——
  这三类采集按下载量取头部，28 条长尾没有。所以 `数据量级(条)` 这类列**本次给不出**，
  不是「这批库没有数据」，是「我们没抓」。要补需另开采集（`enrich --ids` / `fetch-sizes` /
  `fetch-files` / `fetch-readme`），不在本单口径内。
- **数值是交付那一刻的快照**。下载量、点赞、趋势分每天在变；重跑同一条需求，列会跟着变。
  同一版底库 + 同一份输入重跑逐字节一致，跨日重跑不会一致——`manifest.source.current_md5`
  是分清这两件事的唯一凭据。
- **简介会被 HF 截断**（末尾附「见数据集页」），不是全文；全文在 README 表里，未抓。
- **原件在受理后被 Excel 另存过一次**（2026-11-17 17:27 前后，`Downloads` 里的那份从
  10,303 字节涨到 13,044 字节）。已于同日逐格复核：29 行 × 3 列**一格未变**，只是样式与
  文档属性被重写。`input/` 里保留的仍是受理那一刻的快照（sha256 `f522886a…`），档案里的
  指纹说的是它；将来若有人拿 Downloads 里的原件去比 sha256，会不相等——原因就是这个，
  不是我们改过表。
- **对方表若加列**（处理人、质检结果这类内部流程列），本份 spec 不声明、引擎不碰；
  若对方把某列改名成与我们追加列同名，交付会因「表里已有该列」走填充而非追加，
  届时按新表重新升版。
