# 过程记录：REQ-0001 高热度数据集清单

查询型需求的方法就是**口径本身**：没有一次性脚本，没有人工判读，只有一个定义
清楚的筛选条件加一次可重跑的查询。所以这份文档的重心不在「跑了什么」，
而在「每个词条到底指什么」——那是唯一会出错的地方。

## 目标

给出一份「同时有下载量与点赞量的成熟数据集」清单，供选型参考。做完的标准：

- 条件只有两条，且每条都落在词表里一个定义明确的词条上；
- 交付字段是默认底库契约（`data/exports/datasets.parquet` 的 31 列），不是宽表全部列；
- 同一版底库重跑，产物逐字节一致。

## 步骤

1. **定口径**：两条条件——`下载量 > 1000`、`点赞数 > 1000`。
   两个词条的含义以 `GLOSSARY` 的「交付口径」一节为准，不在 spec 里另立定义。
2. **定投影**：不写 `output.columns`，即按默认交付契约投影（契约版本记在
   `manifest.projection.default_columns_version`）。
3. **预演**：`request run REQ-0001 --dry-run`，看行数是否合理（几百到几千量级）。
   0 行或几十万行都说明口径写错了，回去改 spec。
4. **交付**：`request run REQ-0001`。
5. **复核**：读交付目录的 `README.md`，逐条核对条件表与行数；对不上就说明口径变了。

## 机器算的 / 人判的

| 环节 | 谁做 | 判据 |
| --- | --- | --- |
| 筛选、排序、投影、落盘、校验和 | 引擎 | `spec.yaml` 的 criteria / order_by / output，编译成一条只读 SQL |
| 「下载量」取 30 天还是累计 | 人（一次） | 页面显示的口径是近 30 天；累计值普遍大一个量级，故用 `downloads` |
| 阈值 1000 | 人（一次） | 「成熟」= 两个信号都过千；只卡一个会被纯下载量大的库淹没 |
| 排序 | 人（一次） | 按下载量降序——清单是给人从上往下看的 |

## 脚本

无。这不是省事，是这一类需求的正确形态：口径全部落在 `spec.yaml` 里，
执行体是引擎的一部分（`delivery._query_payload`）。为了「有个脚本」而写一个
只是转手调用 `request run` 的脚本，只会多一份需要同步的东西。

## 环境

- 底库：`data/exports/datasets.parquet`；本次交付基于哪一版，见
  `deliveries/20261108T152943/manifest.json` 的 `source.current_md5`
- 代码：`hf-data-crawl` 版本与提交号，见交付档案 `method.env`
- 词表：`src/hf_data_crawl/metrics.py`（词条 → 字段 → 定义），词条定义随包版本变动

## 已知边界

- **「下载量」是近 30 天**，不是历史累计。要累计口径请写「累计下载量」，
  两者差一个量级，混用会让清单看起来「突然少了一半」。
- **空值不参与比较**。某库没登记下载量时 `downloads > 1000` 为假，会被排除——
  这是有意的，不是漏算。
- **只覆盖底库有的库**。底库是 HF 全量对账后的快照，不含私有库与已下架库；
  清单的「全部」指的是「底库里的全部」。
- **默认契约 31 列**不含卡片明细。要 `tags`、`arxiv_ids` 这类扩展字段，
  在 `output.columns` 里点名或用 `query` 直接取宽视图。
