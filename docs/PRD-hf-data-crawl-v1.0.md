# PRD — Hugging Face 数据集元信息底座 v1.0

## Problem Statement

大帅需要长期、可靠地掌握 Hugging Face 上公开数据集的元信息全貌：谁新上架、谁在涨、谁下架、标签体系怎么变。现状有三个痛点：

1. **手工查不可行**：几十万数据集，网页端只能看头部榜单，无法按任意维度切分。
2. **只看当下，看不见变化**：网页给的是此刻快照，拿不到「上周 downloads 涨了多少」这类相对量。
3. **字段随时会变**：今天想要的标签，下个月可能换成别的，重新抓一遍的代价极高。

## Solution

一个跑在本机、可周期执行的采集与加工流水线：

- **每日**按 `lastModified` 倒序增量扫描，抓到水位线即停，捕获新上架与刚变更的数据集；
- **每周**按 `createdAt` 稳定序做一次全量核对，标出下架集、补回遗漏、校正 `sha`；
- 原始响应原样留存，结构化字段由银层派生——**加字段不重抓**；
- 指标变化才追加观测行，因此「近 7 日增速」可一条 SQL 得出；
- 对外只有四个子命令：`collect`、`reconcile`、`build`、`query`。

## User Stories

1. 作为数据选型者，我想看到近 7 日 downloads 增速最快的数据集，以便在它成为共识前就发现。
2. 作为数据选型者，我想按 `task_categories`、`languages`、`size_categories`、`license` 组合筛选，以便快速圈定可用候选。
3. 作为数据选型者，我想知道某数据集是何时上架的、首见与最近一次观测分别是什么时候，以便判断它是新秀还是老库。
4. 作为数据选型者，我想区分 30 天下载与累计下载，以便识别「总量大但已凉」与「总量小而猛涨」。
5. 作为合规关注者，我想按 license 与 `gated` 过滤，以便排除不可商用或需申请的库。
6. 作为维护者，我想在采集中断后从断点续跑，而不必从头再来，以便代理抖动时不浪费数小时。
7. 作为维护者，我想重跑同一轮采集得到完全相同的结果，以便失败重试不会污染数据。
8. 作为维护者，我想知道某轮采集实际抓了多少页、消耗多少配额、剩余配额多少，以便提前发现限流风险。
9. 作为维护者，我想在采集前只探一页，确认字段与连通性，以便不把一次失败留到几小时后才发现。
10. 作为维护者，我想在全量核对后得到「新增 / 下架 / 字段变更」三类清单，以便判断外部世界发生了什么。
11. 作为维护者，我想已下架的 Dataset 保留其历史观测，只标记状态，以便趋势不出现断崖。
12. 作为维护者，我想原始响应永久留存，以便任何时候用新规则重算银层而不联网。
13. 作为维护者，我想用一条命令从原始响应重建全部派生层，以便修复派生逻辑的 bug。
14. 作为分析者，我想直接用 DuckDB 对 parquet 写 SQL，以便不必等我把每个查询都做成功能。
15. 作为分析者，我想榜单是视图而非实体表，以便口径改了立刻生效。
16. 作为分析者，我想标签被拆成可 join 的维度，以便按标签聚合而不是字符串模糊匹配。
17. 作为预算敏感者，我想日扫描用 lean 档、只在必要时取 `cardData`，以便把每日成本压到半小时内。
18. 作为运维者，我想看到每次运行的耗时、页数、字节数、失败重试次数，以便判断系统是否在退化。
19. 作为运维者，我想在配额耗尽时自动等待而非失败，以便无人值守也能跑完。
20. 作为运维者，我想在数据结构异常（缺 `id`、缺 `lastModified`）时跳过该条并记录，而不是整轮崩掉。

## Implementation Decisions

- **分层固定为 Raw → Bronze → Silver → Current/Observations → Gold(视图)**，各层职责见 `GLOSSARY.md`。
- **两档采样**：`collect` 日跑用 Lean 档（无 `cardData`）；`cardData` 与新记录详情在 Silver 构建阶段按需补齐。理由：实测 full 档 5.9 MB/千条、90–170 KB/s 带宽下全量要数小时，而日增量的信息量几乎全在身份与指标字段。
- **排序显式化**：任何遍历都必须传 `sort`。全量核对用 `createdAt`（不可变，游标稳定）；日增量用 `lastModified&direction=-1`。禁止依赖默认序。
- **Watermark 采用「连续 N 页无新记录」判定**，而非 `max(lastModified)`。实测存在 2028 年异常时间戳，任何单调性假设都会导致漏抓或空转。
- **断点续爬**：每页处理完即原子写 checkpoint（`cursor`、`snapshot_date`、已处理条数、已完成标志）。checkpoint 与数据同事务语义——先落 Raw，再更新 checkpoint。
- **幂等写入**：Bronze/Silver 按 `(id, snapshot_date)` 去重；Current 整表由 Silver 最新态重建；Observations 以 `(id, snapshot_date)` 为键，同日重跑覆盖而非追加。
- **HTTP 传输可注入**：`HfDatasetApi` 接受一个 transport 参数，生产用真实 HTTP，测试注入假 transport。这是全项目**唯一**的外部边界。
- **认证与代理走环境变量**：`HF_TOKEN`（可选，缺失则匿名）、`HF_PROXY`。绝不硬编码。
- **限流处理**：解析 `RateLimit` 头，剩余配额低于阈值时按 `t` 等待；429/5xx 指数退避，最多重试 5 次。
- **存储栈**：polars 读写 parquet，DuckDB 建视图查询；不使用 pandas。
- **CLI 四子命令**：`collect`（日增量）、`reconcile`（全量核对）、`build`（从 Raw 重建派生层）、`query`（执行 SQL 或打印内置榜单）。全部支持 `--dry-run`。

## Testing Decisions

- **好测试的定义**：只验外部行为——给定输入页，产出什么行、什么 checkpoint、什么退出码；不验私有函数、不 mock 内部协作者。
- **主 seam（唯一新增边界）**：`HfDatasetApi` 的 transport 注入点。所有分页、退避、字段构造、异常跳过都在这条缝上验。
- **次 seam**：`Store` 的公开方法（`write_raw` / `upsert_current` / `append_observations` / `rebuild_silver`）。幂等性与同日重跑覆盖在此验。
- **端到端 seam**：CLI 子命令 + 临时数据目录 + 假 transport，验「中断后续跑得到与一次跑完相同的结果」。
- **不测**：DuckDB 的 SQL 正确性不写单元测试（SQL 由视图定义保证），改由一条金标查询的端到端断言覆盖。
- **Predecessor**：本仓当前无既有测试，这是第一批。测试用 pytest，命名遵循「行为句」而非「函数名」，如 `test_中断后从checkpoint续跑不重复入库`。

## Out of Scope

- 下载仓库内的实际数据文件或用 datasets-server 拉样本行。
- 私有数据集（需账号权限，且与「公开底座」定位不符）。
- 模型（models）与空间（Spaces）的同类采集。
- 榜单的 HTML 可视化页（v1 只到 SQL/表格）。
- 多机分布式采集与队列化调度。
- 自动提交到远端仓库或发布（本地落盘为准）。

## Further Notes

- 全站总量尚未实测（列表接口不返回 `X-Total-Count`）。首轮 `reconcile` 会自然得出该数字，届时据此校准调度窗口。
- 代理链路吞吐是本系统的主要物理约束。若首轮全量超过 8 小时，应优先考虑把采集迁到服务器，而非加并发——限流还剩 400+ 次配额，瓶颈在带宽。
- `trendingScore` 只存不用：它是 HF 的黑盒打分，口径不透明，榜单以自算 `downloads` 差值为准。
