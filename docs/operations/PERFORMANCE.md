# 性能与体积基线

> 这份文件回答「数据现在多大、查得多快、各表压得多紧」。数字会过期，所以每条都
> 带日期；重测就往对应日期下追加一节，**不改写旧数字**——它们是与当时那次改动
> 对照的证据。
>
> **各机器的 `data/` 互相独立**（代码共享、数据不共享）。下面所有体积与行数都
> 来自一台机器，跨机器只比**方法与相对变化**，不要拿绝对数字互相对照。

## 怎么重测

```bash
uv run python scripts/tools/bench.py            # 打印一份 Markdown 报告
```

它只打印、不判红：基准会随机器、负载与数据量漂，硬阈值只会训练人忽略告警。
把输出贴到本文对应日期的小节里，与上一次比。

## 压缩参数（2026-11-18 起）

parquet 的压缩级别写在 `platform/tables.py` 的 `TableSpec.compression_level`，
`store.write` 按它写盘。**只有冷表调高**：

| 表 | 级别 | 理由 |
| --- | --- | --- |
| `readme` | 12 | 整库最大单表（357 MB / 3 GB 文本），只在 `readme` 视图按 id 查。写一次 94 秒换 61 MB 是划算的；按 id 查 0.05–0.17 秒，与物理排序关系不大（见下面第 4 条） |
| 其余全部 | 默认（3） | 热表实测查询 ≤ 1.3 秒、`COPY` 全量导出 14 秒，瓶颈不在压缩；调高只会让每次派生写盘变慢，调低只换来 7% 写速却让文件大一圈 |

`raw/` 的分块用 zstd level 3（`pipeline/raw._LEVEL`）。这是 2026-11-16 实测的
拐点：同一页 1090 KB，level 3 压 4.7 ms / 281 KB，level 1 只快 2 ms 却大 12%。
冷区基线（`compact` 产物）跟随同一级别——它是 `build --full` 的输入，压太狠会
拖慢全量重放。

**注意**：parquet metadata 只记 codec（`ZSTD`），不记级别，所以**没法从落盘文件
反查**。改过 `compression_level` 之后必须重写一次该表才生效，并在这里更新。

## 已知结论（2026-11-18）

1. **性能不是瓶颈**：所有查询在 1.3 秒内，导出 14 秒。`export-wide` 曾被误报成
   「20 分钟」，实测是等数据锁——`COPY` 本身只要 8–14 秒。
2. **磁盘大头是冷表**：`readme` 357 MB 占全库 15%，且只在按 id 查时用；`raw` 热区
   974 MB 是 7 天重放窗口的代价（冷区基线生成后会稳定）。
3. **压缩级别对热表无收益**：zstd 3 → 12 只省 15%，写盘慢 2.4 倍；→ 19 省 24%，
   写盘慢 13.6 倍。文本列在 level 3 已接近饱和，再压要改结构（拆表/归档正文），
   不是调参数。
4. **`readme` 的按 id 查询与物理排序关系不大**（2026-11-19 实测）：`store.merge_by_id`
   为省内存刻意不排序（`upsert` 才 `sort("id")`），理论上会让 row group 的 zone map
   失效——新追加的 group 的 id 范围覆盖全表。但实测两种形态（有序 vs 追加一个覆盖
   全表的乱序 group）单 id 查询中位 **17.07 vs 16.30 ms**，没有显著差异；给 id 列加
   parquet bloom filter 也只让文件从 21.4 涨到 23.6 MB、耗时 206 → 201 ms。
   原因是查询只读 `id` 一列，列裁剪后 I/O 很小，开销主要在文件绑定与元数据。
   **结论：不必为此定期重排，也不必加 bloom filter。** 这条基线记的是「有序时的
   最好情况」，但排序与否测不出差别。

## 变更记录

### 2026-11-22：观测流水改为分层采样

上面两张体积表是 11-18 的快照，观测那一行（215 万行 / 67.6 MB）此后已不可直接对照，
原因有三层，按时间顺序：

1. **11-19 的 `refresh` 链**让 `collect --full-scan` 与 `reconcile` 各扫一遍全站，
   `raw` 每日分块从约 1,160 涨到 2,300+（已于 11-22 修掉，见 ADR-0009）。
2. **11-21 的落盘去重**（DECISIONS #165）让两份全站快照的第二份只落差异，
   `raw` 每日回落到约 166 MB。
3. **11-22 的分层采样**（DECISIONS #168）让 `observations` 从「每次变化都记」变成
   「头部 2 万名每天记、长尾按 id 哈希每周轮一天记」：当日 623,986 条变化只落
   106,402 行（17.1%），单日分区 20 MB → 6.2 MB，年化 7.3 GB → 2.3 GB。
   热区七天重放后总行数 1,046 万 → 775 万，`state/observations` 311 MB → 240 MB。

**对性能基线的影响**：`榜单 growth（扫 215 万行观测）` 那一行的前提已变——观测表
小得多，榜也不再按区间累计增量排，而按 `growth_daily`（复合折算的日均）。两种排序
都需要扫全表算 `row_number()`，耗时量级不变（仍在 1 秒级），但**结果集不同**：
头部与长尾的 `span_days` 不再相同，跨库比较必须走日均列。

**未变的结论**：第 1、2、3、4 条（性能不是瓶颈、磁盘大头是冷表、压缩级别无收益、
readme 排序无关）都不受采样影响。
