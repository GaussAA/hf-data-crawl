# ADR-0004: 失败也要有下文——交付失败的版本号、台账与自证锚点

**日期**: 2026-11-17
**状态**: 已实施
**修订**: 部分推翻 ADR-0003 落地时保留的一条旧约定（失败保留口径快照）

---

## 背景

ADR-0003 之后对需求管理与交付系统做了一轮审计，找出四类「不报错、但会让档案失真」的
缺陷。它们有一个共同点：**失败路径没有下文**。

1. **失败的交付会占掉版本号**。`snapshot_history` 在 `try` 之前落盘，产物计算、护栏、
   重复闸门、写档案全在之后。于是改口径、升到 v3、第一次跑被 0 行拦下——`history/v3.yaml`
   已经在了。把口径修好、仍用 v3，`version_conflict` 报「v3 已被占用」：**什么都没交出去，
   却被迫跳到 v4**。旧约定是「宁可多一条从未交付的快照」，理由是「反过来在改名与快照之间
   崩溃，会留下产物已出土、history 没有这版」。这两件事其实不同：**崩溃**来不及收，
   **可处理的失败**收得回。
2. **需求侧的失败没有台账**。`request run` 绕开 `_execute`（`cli.py` 的 request 分支），
   不写 `runs/`。于是「近 7 天没有未恢复的失败运行」只看得到采集侧的失败；一次被拦下的
   交付除了终端滚过去的那几行，什么也不剩。
3. **交付锚点没人对账**。档案里的 `fill.input.sha256` 与 `history/vN.yaml` 是自证链；
   输入快照被就地改过、或历史快照被删掉，都不会报错——后者会让 `version_conflict`
   从那一刻起对那一版静默失效。
4. **数值写错会穿透**。`header_row: 不是数字`、`width: 很宽` 走裸 `int()`，抛
   `ValueError`：`request new` 留半成品、`doctor` 整份崩、`run-due` 带栈中断。

## 决策

### 1. 可处理的失败要回滚版本快照

「先快照、后改名」的顺序不变（崩溃窗口仍需它兜底），但**发布失败时删掉本次新建的那份
快照**：判据是「这次运行有没有产物换名成功」。只为本次新建的回滚——别人早就落下的不动，
重复闸门那种「同内容再交一次」本来也不会新建。

### 2. 需求侧也进运行台账

`request run` / `run-due` 改走 `_execute`：拿同一把数据锁、写 `runs/<时刻>-request-run.json`，
失败也写并带原因。`--dry-run` 与 `--preview` 除外——草稿不记账，否则「最近的失败运行」
会被一堆预演淹没。

### 3. 交付锚点单独入体检

新增 `delivery_anchors` 检查项：逐份交付对账

- `spec_version` 对应的 `history/vN.yaml` 必须还在；
- `fill.input.path` 指向的输入快照必须还在，且字节 sha256 与档案记的一致。

两项都按**档案里记的值**比，不按「今天的 spec 应该是什么」——后者随代码演进漂移，
历史交付没有义务重算成今天的口径。

### 4. 数值项与格式错配一律翻成口径错误

`backfill._int` 负责整数项（`header_row` / `width`），`_format` 把 `gb` / `int` 的转换
失败翻成 `FillError`；执行体再把 `FillError` 翻成 `DeliveryBlocked`。`run-due` 逐条
兜 `OSError` / `ValueError`：坏的报出来，好的照常出。

### 5. 交付只读一次 spec

`requirement.loads` 从**已读入的文本**解析；交付时读一次字节，校验、`spec_sha256`、
历史快照三处共用。归档的三样东西从此同源，不再出现「校验旧版、快照新版」。

### 6. 交付目录的写点全部原子化

`INDEX.md`、`history/vN.yaml`、`method.json`、输入快照收编改走 `platform.atomic.write_bytes`。
索引写在交付落盘之后，且**失败只告警**：目录已经换名成功，此时报「交付失败」只会让人
再跑一次、再被重复闸门拦住。

## 不采纳的方案

- **失败一律不落快照（把 `snapshot_history` 挪到改名之后）**：回到 ADR-0003 之前的风险
  ——崩溃时产物已出土、history 没有这版，版本号静默可复用。可处理失败与崩溃必须区别对待。
- **让 `version_conflict` 忽略「没有对应交付的快照」**：等于把崩溃窗口重新打开，而且
  「有快照没交付」在历史数据里本来就有（REQ-0004 之前的一次失败尝试）。
- **把索引写失败算成交付失败**：目录已在，报失败会诱发重复交付；索引缺失本来就是体检项。

## 后果

- **失败会出现在 `runs/` 里**：`request-run` 与 `request-run-due` 成为台账里的命令名，
  `reason` 记的是「被哪道闸门拦住」的完整一句话。一次被拦下的交付从「只有终端记得」
  变成「可查询、可统计」。
- **但单次 `request run` 的失败不进体检红点**。它由人当场发起、当场看见，而「今天没有
  新信息」「代码还没提交」都会走到失败——算进「近 7 天未恢复失败」，一次正常拒绝就能
  让告警亮一周。`request-run-due` 不同：那是没人盯着的定时路径，坏了照常报。
- **`runs/` 会变多**：只记正式交付，不记预演/预览。定时链的 `run-due` 每天最多一条。
- **版本号可以「重来」**：护栏拦下后改口径不必再跳版本——但内容改过之后仍要升版，
  `version_conflict` 只对「快照里那一版」生效。
- **体检多一项**：`delivery_anchors`；历史交付（REQ-0001..0004，其中 0001..3 是开发样例）实测全绿。

## 回滚

四处互相独立：

- 版本号回滚：删掉 `deliver()` 里的 `created_history` 判定与 `unlink`。
- 台账回滚：`cli.py` 的 request 分支退回直接调用（不再写 `runs/`）。
- 锚点检查：删 `CHECKS` 里的 `delivery_anchors` 一行。
- 只读一次：`load_spec_text` 改回 `load_spec(spec_path)`。
