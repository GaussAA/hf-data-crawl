# ADR-0003: 交付档案治理——闸门、预览与索引

**日期**: 2026-11-17
**状态**: 已实施

---

## 背景

2026-11-17，需求 REQ-0004（28 条开源 query 轨迹数据集字段拼接）在一天内留下了 **5 条交付**。
对方问：为什么这么多？中间三条是什么？测试性结果不该放在交付目录里——这是不是需求管理体系的问题？

复盘事实（`deliveries/` 下 5 条的 manifest 逐条比对）：

| 时刻 | 版本 | 列数 | 产物 sha256 | 当时工作区 | 性质 |
|---|---|---|---|---|---|
| 17:30:45 | v1 | 23 | `8707d1ba` | 有未提交改动 | 首版 |
| 17:31:49 | v2 | 23 | `07488652` | 有未提交改动 | 只补 8 列列宽，格子值 0 差 |
| 17:36:19 | v2 | 23 | `07488652` | 干净 | **纯档案修补**（重钉 commit） |
| 17:51:59 | v3 | 39 | `08a1eae6` | 有未提交改动 | 真实内容扩展（上游补采 16 列） |
| 17:55:35 | v3 | 39 | `08a1eae6` | 干净 | **纯档案修补**（重钉 commit） |

两条是逐字节相同的「重钉」；一条是排版返工；两条的 manifest commit 复现不出各自产物。
继续查，这不是孤例：REQ-0003 的 v1 与 v2 产物 sha 完全相同（`request diff` 说「口径未变，
只有交付节奏 once→manual」），9 次交付里有 3 次产物逐字节重复。

根因有三层：

1. **档案层**：`manifest.method.env.commit` 只记 `git rev-parse HEAD`，不记工作区是否脏。
   脏着交付 → 档案声称来自某提交、实际不是；唯一的补救是提交后重跑一次，于是多一条
   内容相同的条目。
2. **交付形态**：`request run` 成功即一条交付；`--dry-run` 只给文本、不给能打开的产物。
   于是「想看一眼真表」的唯一办法是正式交付——排版问题只能交付后才发现并回头修。
3. **交付语义**：每次运行都记一条，哪怕底库与产物都没变。触发条件绑在「spec 文件变了」
   上，改节奏、改标题、补一次 commit 都要靠重交来记账。

另外两条早期根因更值得记：**受理时没定死「字段清单从哪来、要不要爬上游」**（REQ-0004 先交了
两次「底库现有」的表，对方才说可以爬），以及**执行时在脏工作区上交付**（本可以先 commit）。

## 决策

### 1. 预览产物与干跑分开

新增 `request run <id> --preview`：把真产物写进 `<需求目录>/scratch/preview/`，附一页
`PREVIEW.md`；固定路径覆盖写、不进台账、交付成功后删除、`scratch/` 进 gitignore。
`--dry-run` 保持「只看不写」。

### 2. 出口闸门

- **脏代码不出版**：查 `src/` + `pyproject.toml` + `uv.lock`；脏 → 拒绝，提示先 commit
  或用 `--preview`。manifest 新增 `worktree` 段（checked / clean / paths）留痕。
  不留 `--allow-dirty` 逃生舱。
- **没有新信息不记账**：与上一条交付比「底库指纹 + 产物字节」，两样都没变 →
  `DeliveryUnchanged`；`request run` 拒绝并指路旧目录，`run-due` 记「跳过」。
  底库变了而产物没变放行（那是有效的复核观测）。

### 3. 交付索引

交付后自动重写 `deliveries/INDEX.md`（`request index` 可单独补建）：列出每条的性质
（据产物字节、列集、版本号自动推断）、可复现性、产物 sha、底库 md5、commit，并标出
「当前有效」；末尾一行机读标记供 `doctor` 判过期（不按 mtime）。`deliveries/AUDIT.md`
是唯一的人工文件，记录引擎事后无法重算的事实；INDEX 读它的 ```json 段填「可复现」列。

### 4. 展示项不占版本号

`width` / `wrap` 从「口径指纹」中移除（`spec_core_digest`），版本号是否可复用按它判；
档案指纹（`spec_digest`）仍含展示项，因为产物字节确实会变。`request diff` 把展示项
单列一段，与「口径差异」「不影响产物的字段」三分。

### 5. 需求成立性先行

`METHOD.md` 骨架新增「需求成立性」一节（症状 / 成因 / 照做会不会丢证据）；`hf-request`
skill 把它列为第一步，并要求受理时定死字段清单与上游成本。缺这一节时 `request method`
只提示、不拦交付——写成必填，最先发生的永远是抄一句过闸。

## 不采纳的方案

- **清空 / 归档被取代的交付**：交付目录是台账，不是货架。删/移会一起毁掉 previous 链、
  compare 历史与这次能点破的历史事实。缺的是「哪条算数」的指针，不是「条目少」。
- **`--allow-dirty` 逃生舱**：留下口子后，「档案记的 commit 能复现产物」这句承诺又会
  变成概率事件；真急着看产物，`--preview` 已经够用。
- **脏了就记 `dirty: true` 而不拦**：诚实但没用——那份交付依然不能被别人复现，而它
  看起来与干净交付一模一样。宁可让作者先花十秒 commit。

## 后果

- **定时链会因脏代码变红**：`run-due` 走同一道闸门。当前 4 个需求都是 `manual`，实际
  影响为零；将来若有人一边改 `src/` 一边指望每日交付，会撞上这道门——那是期望行为。
- **历史档案不再完全可复算**：`spec_digest` 的投影变了（展示项移出口径指纹只影响
  `spec_core_digest`，`spec_digest` 未变），故旧 manifest 里的 `spec_sha256` 仍可重算一致。
- **REQ-0004 不重交**：INDEX 与 AUDIT 是对历史的事实记录，不新增第 6 条。
- **INDEX 由引擎生成**：人只读不改；改了下一次交付会被整份覆盖。

## 已知

下面两条是落地当天就撞上的，记事实、不改判据——它们都不是这套能力的错，但会让人误读体检或档案。

### 1. 并发会话：闸门管不了同一台机器上的别人

2026-11-17 20:12，同一仓库上另一个会话在跑新加的 `fetch-preview`，撞 429 整轮中止，
`runs/` 里留下一条未恢复的失败，`doctor` 因此有一个红点。同一时段它还把工作区里
`src/hf_data_crawl/acquire/` 的改动带在树上，于是 `request run REQ-0004` 先被**脏闸门**
拦下——拦得没错，但拦的是别人的改动。

- **判据的边界**：脏闸门只回答「这台机器上，`src/` 里有没有会被记进 manifest 的未提交
  改动」，它不区分改的人是谁，也不管别的会话正在写 `data/`。
- **怎么办**：真并发时各自开 worktree（`create_worktree`）各提各的分支，别在同一分支上
  同时改 `src/`；或者约定「谁要交付，谁先把工作区清干净」。
- **不要把这条红点当成闸门的缺陷**：它正是闸门在说实话——那一刻的代码确实不是从某个
  提交里长出来的。

### 2. 脚本指纹会与磁盘漂移：那是格式化的代价，不是伪造

`manifest.method.scripts` 与 `method.json` 钉住 `method/scripts/` 逐份 sha256。之后若对
交付脚本做纯格式化（实例：`7876a73` 把 REQ-0004 的两个脚本按 `ruff format` 重排并重算
了索引），磁盘上的脚本与旧交付档案里记的指纹就分叉了。

- **这份档案还算数吗**：算。它解释的是「当时跑的那份脚本长什么样」，而纯格式化不改
  行为（该次改动 `ast.parse` 通过、逻辑一字未动）。要逐字节复现当时的产物，得按旧
  指纹从 git 历史里取回那一版脚本。
- **什么时候消掉**：下一次交付会重钉当前脚本的指纹。想提前对齐，跑
  `request method <id>` 重算索引，再让 `doctor` 看「交付索引」那一项。
- **为什么不在 `doctor` 里加「脚本指纹与最近一次交付不一致」的检查**：纯格式化会让它
  一直红，而红的原因与「数据不可信」无关——体检项一旦变成噪音，真正的问题就会被
  一起忽略。宁可让这条留在 ADR 里，由人决定是重交一次还是按旧指纹取回脚本。

## 回滚

三项能力互相独立，可分别回滚：

- 去掉 `--preview`：删 CLI 参数与 `preview(keep_files=)`，`scratch/` 自然不再产生。
- 去掉闸门：删除 `deliver()` 里的 `_worktree_gate` 与 `_refuse_unchanged` 两次调用。
- 去掉索引：删 `write_index` 调用与 `doctor` 的 `delivery_index` 检查项；`INDEX.md`
  是普通文件，删掉不影响任何 manifest。
