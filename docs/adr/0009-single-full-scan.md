# ADR-0009：全站扫描只做一次——对账复用当天分块

- 状态：已实施（2026-11-21）
- 日期：2026-11-21
- 决策者：作者
- 取代：本文档初版（同日早先）记录的「暂缓」结论

## 背景

ADR-0008 把日常链定成「串行头 `collect --full-scan` → `build` ‖ 并行段 `reconcile`」。
审计请求数才发现，一天里对**同一个列表接口** `/api/datasets` 发了四趟请求：

| 趟 | 参数 | 页数 | 与主扫描逐字段相同 |
|---|---|---|---|
| `collect` 主扫描 | sort=lastModified，`--full-scan` | 1,141 | — |
| `collect` 顶部池 | sort=downloads，头部 2 万 | 20 | **99.0%**（19,792/20,000） |
| `collect` 变化集卡片 | 多带 `cardData` | 5 | 37.3% |
| `reconcile` | sort=createdAt，全站 | 1,141 | **99.9%**（1,140,360/1,140,936） |

2,307 页里有 1,161 页是**为同一批资源、同一天、第二次（第三次）开口**。这不是
存储问题（重复落盘已由 DECISIONS #165 解决），而是请求与时间本身的浪费。

判据很简单：**如果一个接口一次就能把需要的字段给全，就不该为不同字段反复问同一个
资源。** 顶部池那趟连字段都没换，只是换了个排序再取一遍同样的 2 万条。

## 逐趟处理

### 删掉：`--full-scan` 下的顶部池刷新

主扫描已扫完全站，头部 2 万条必然含在里面；实测 99.0% 逐字段相同。增量扫描
（未扫全站）时它仍然必要——那时主扫描只覆盖最近更新的万把条，头部确实没有
第二天的读数。故判据是 `full_scan`，不是「删掉这个功能」。

### 改掉：`reconcile` 不再自己扫全站

对账需要的信息只有两件：「这一天见过谁」与「它们是什么 sha」。这两件当天的
采集分块里全都有——`ReconcileSession.remember` 本来也只取 `record["id"]` 与
`record.get("sha")`。

于是 `reconcile` 默认改为 `read_seen(store, snapshot_date)`：读当天 `part` 分块，
同一 id 取 `written_at` 最晚的那条（与 Bronze 的胜负同口径）。**1,141 页全站扫描
变成一次本地读取。**

### 不动：变化集卡片

`cardData` 让记录变胖。实测变化集 5,000 条约 1.3 MB，而主扫描 1,140,892 条约
165 MB；把 `cardData` 并进主扫描的 `expand`，对有卡片的库（约 78 万，doctor 报
卡片覆盖 68%）每条多 200 余字节——总量估约 ×2.2。**省 5 页换 200 MB 带宽，
是负收益。** 卡片只对变化集有意义，保持单独一趟。

## 四条不可协商的边界

1. **完整性判据换成「采集扫完了没」**。从前看对账自己那趟的 `stopped_reason`，
   现在看它所依赖的采集：`collect` 的 run 台账 `stopped_reason == "end"`
   （复用 `platform.runs.last_success` + `FULL_SCAN`）。不完整则 `incomplete_collect`，
   只出差异清单、不判下架——把没扫到的部分标成下架是不可逆的。
2. **当天没有分块时退化到自己扫**。`collect` 未跑或失败时，若坚持「读分块」就等于
   拒绝服务；退化后本轮的分块就是那天唯一的数据源。所以 `reconcile` 单独跑仍然可用。
3. **保留 `--scan` 逃生舱**。分块可疑（来源混杂、内容异常）时强制自己扫一遍。
   删掉它等于把「对账」与「采集」绑成死结，而它们本该能分开排障。
4. **空集合不能当成「全站下架」**。`read_seen` 返回空时走退化路径而不是产出一份
   差异清单——那一刻的清单会包含全部基线 id。

## 实测

- `read_seen(2026-11-21)` ＝ **1,140,942 个 id / 26.7 秒**（当天 2,307 片，
  含 P1 之前遗留的 reconcile 分块；明天的规模只读 collect 的 1,141 片，约 13 秒）；
- `collect_completed` ＝ True，sha 为空的记录 0 条；
- 每天请求数 **2,307 → 1,146 页**（−50%），墙钟省下一次全站扫描的 12–20 分钟。

## 与「暂缓」结论的关系

本文档初版以「存储收益已被 P1 吃掉、只剩 15 分钟」为由暂缓。该判断漏了一层：
**省下的 1,141 页不是 15 分钟的成本项，而是「同一份数据问第二次」这件事本身**。
收益怎么算取决于在优化什么——按存储算它归零，按请求数与墙钟算它是一半。
作者最终按「不该重复问同一个资源」这条原则批准实施，而非按单日分钟数。
