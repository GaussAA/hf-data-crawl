# ADR-0008：刷新链改为「采集定稿 + 对账‖enrich + 收尾」的每日窗口

- 状态：已接受
- 日期：2026-11-19
- 决策者：作者

## 背景

旧的刷新逻辑是「一条串行 daily 链 + 五个独立周任务」：

- `hf-daily` 03:10：collect → build → reconcile（600 页分批）→ sizes（8000 名额）→
  export → deliver → prune → doctor；
- `hf-compact` 每日 00:30、`hf-archive` 周一 05:00、`hf-sizes` 周日 06:00（全量）、
  `hf-files` 周日 07:30（前 1000 名）、`hf-readme` 周六 09:00（8000 名额）。

2026-11-19 的复盘暴露四个问题：

1. **对账永远扫不完**：`--max-pages 600` 是分批续扫，但铁律「只有扫到末页才判定
   下架」意味着每轮都在续、从不在同一轮里看到全站。
2. **enrich 有名额上限，短板永远在**：readme 每周只取 8000 个、sizes 每周只取
   8000 个、files 只覆盖前 1000 名、card 有 200 页上限。当天变了的下游数据要等
   一周才可能被刷到。
3. **卡片的尾部永不保鲜**：`collect --refresh-top 20000` 只刷头部 2 万名的
   cardData。
4. **周任务靠钟点错开，且不补跑**：错过就等下一周。

作者同时确认：`hf-update`（另一个项目）的抓取已永久暂停，API 配额不再需要
在两个项目之间分配。新的要求是：

- 对账不设页数上限，一轮扫完全站；
- enrich（sizes / readme / carddata / config）每日刷新，不设名额，迎新补旧；
- files / preview 每日刷新，固定增量 + 更新存量（它们限速严，全量慢）；
- 取消全部周任务；
- 每日 00:30 开始，到 09:00 为止。

## 关键约束（实测）

| 命令 | 全量代价 | 依据 |
|---|---|---|
| `fetch-readme` | 约 22 小时 | 113.8 万条 × 限速 15 req/s（HF resolver 5000/5 分钟） |
| `fetch-sizes --top 0` | 约 9.8 小时 | 周日实测 35,189 秒 |
| `fetch-files --top 20000` | 70 分钟 | 最近一次 4,201 秒 |
| `reconcile` 600 页 | 中位 399 秒、最大 1,833 秒 | 全站约 1,140 页 |

「真·全量重抓」在 8.5 小时窗口内不可能成立，所以口径定为**增量全覆盖**：
候选 = 陈旧 ∪ 缺口，不设名额，跑不完次日续（DECISIONS #135）。

## 决策

### 1. 链的形状：三段式，串并混合

```
① 串行：compact → collect --full-scan → build
          ↓（current 定稿）
② 并行：reconcile（持锁全站扫） ‖ sizes / readme / preview（锁外抓取）
   files 排在 reconcile 之后（同走 /api 配额）
          ↓
③ 串行收尾：各抓取合并（排队短锁）→ export（sizes 合并后即跑）→ deliver → prune → doctor
```

- `collect --full-scan`：新增开关，忽略水位线扫到末页（约 1,140 页、12–20 分钟）。
- `reconcile` 取消 `--max-pages`：一轮扫完，13–60 分钟。
- `fetch-files` 改造为锁外抓取（staging 分片 + 短锁合并），否则它整段持锁会挡住
  整个并行段。
- `export-wide` 在 sizes 合并后立即跑：31 列契约只依赖 `size` 的 `server_*` 四列，
  readme / files / preview 都不在契约里。

### 2. 各表的名额

| 表 | 候选 | 每日量级 |
|---|---|---|
| `readme` | 陈旧 ∪ 缺口，**不设上限** | 日均 5 千，大变化日可达数十万（次日续） |
| `size` | 陈旧 ∪ 缺口，**不设上限** | 日均 6 千（约 4 分钟） |
| `carddata` / `card_configs` | lastModified 变化 ∪ 缺口，**去掉 200 页上限** | 日均数万 |
| `files` | 固定 20,000 + 存量更新 | 约 70 分钟 |
| `preview` | 固定 20,000 + 存量更新 | 约 1 小时 |

### 3. 调度与续跑

- 新建 `hf-refresh`（每日 00:30），删除 `hf-daily` / `hf-compact` / `hf-sizes` /
  `hf-files` / `hf-readme` / `hf-archive` 六个旧任务。
- **软边界 09:00**：到点停下未完成的抓取，staging 分片保留；次日 00:30 从
  「runs 台账成功记录 + staging 是否为空」判断哪些步骤已完成，只跑没完成的。
- 次日启动时若发现上一条链仍在跑，跳过本次触发（不强制重启）。
- 某步失败：依赖它的跳过，不相关的并行分支照常跑；不重试，次日续。
- 超时那天 doctor 照常跑——它是唯一能说明「今天哪里没跑完」的环节，且只读。

### 4. 编排载体

新写 Python 编排器（`ops/refresh.py`，CLI 子命令 `refresh`），不用 PowerShell
`Start-Job`：需要与现有命令共用同一套 runs 台账、锁与退出码语义，而
`_common.ps1` 的日志格式、锁等待、超时处理已经够复杂，再叠一层作业调度只会
出现两份事实。

## 被否的方案

- **真·全量重抓**：readme 22 小时 + sizes 9.8 小时，一天跑不完，且次日 00:30 会
  撞上没跑完的上一天。
- **PowerShell Start-Job 编排**：日志、退出码、锁等待与 `_common.ps1` 重复。
- **两条独立链（数据链 / enrich 链）并行**：共用一把数据锁，收尾合并必然互等，
  复杂度换不到时间。
- **失败即停整条链**：readme 撞 429 会让当天的导出与交付也做不成。
- **保留周任务作为兜底**：周任务与每日链的候选集重叠，等于同一批工作被安排两次。

## 风险

1. **并行段的 429**：`files` 与 `reconcile` 同走 `/api`（1000 请求/5 分钟），所以
   files 排在 reconcile 之后；readme（resolver）、sizes / preview
   （datasets-server）各走不同端点，配额池独立。仍需实测确认并行不会互相拖慢。
2. **collect 全站每天多花 15–20 分钟** API 配额，换来 cardData 的全站覆盖。
3. **08:50 之后启动的抓取可能跑不完**：软边界只停止「未开始的」，正在跑的抓取
   会跑完再结束，实际收工时间可能略晚于 09:00。

## 修订（2026-11-19 落地复核）

决策正文保留原貌，下面是落地时与事实不符、或当时没写清的三处：

1. **契约不是 31 列，是 35 列**（DECISIONS #136）。正文里「31 列契约只依赖 `size`
   的 `server_*` 四列，readme / files / preview 都不在契约里」两处均需按此读。
2. **导出确实依赖 readme**：35 列里的 `paper_url` / `citation_bibtex` 取自
   `readme_fields`，而那张表由 `parse-readme` 从 `readme` 派生。所以链上是
   `readme → parse → export`，`export` 的依赖写全为 `build, reconcile, sizes, parse`。
   正文那句「readme 不在契约里」是 v5 口径的残留。
3. **归档漏了排期**：正文只写「删除 `hf-archive`」，没写它并入哪一段。落地时确实
   没人接——`doctor` 的 `archive_backlog` 一过 30 天就永久报红。现排在串行尾
   （`request run-due` 之后、`prune` 之前），`needs=build`：它要用 build 之后的
   派生状态判「归档前是否已滞后」，改的是 Raw 而非 `current`。
4. **两次全站扫描的第二份不再原样落盘**（2026-11-21，DECISIONS #165）：正文把
   `collect --full-scan` 与 `reconcile` 都写成「全站扫」，但没写它们**覆盖的是
   同一批数据**——11-21 实测两份交集 1,140,886 个 id，其中 1,140,360 条逐字段
   相同（99.95%），差别只有 526 条（两轮相隔 19 分钟里的正常漂移）。原样落两遍
   等于每天多存 165 MB，21 天留存就是 3.4 GB。现改为：`reconcile` 落盘前读当天
   已落分块的记录指纹，只落「当天还没出现过相同内容」的记录，整页重复则一个
   文件都不写。对账的判定、探测、差异清单一律不变——变的只是不再存第二份。
   注意风险 2 的取舍仍然成立：`collect --full-scan` 是**为 cardData 全站覆盖**
   付的 15–20 分钟，不因去重而取消。至于「同一接口一天被问四趟」这件事，
   已在 ADR-0009 处理：全站扫描时删掉冗余的顶部池刷新，`reconcile` 改为复用
   当天采集分块而不再自己扫一遍，请求数 2,307 → 1,146 页。

另有一处实现约定写进代码而未写进本 ADR：`--card-pages 0` / `--max-pages 0` 表示
**不设上限**（命令行惯例），`ScanSpec` 与 `api.scan` 都按这个口径判，照字面比会在
第一页就停。

## 修订（2026-11-20）：`fetch-files` / `fetch-preview` 退出链外

用户拍板把这两步从每日窗口里拿掉，改为**自由抓取**（只在人明确要的时候跑）。
落地的三处改动与理由记在 DECISIONS #149；此处只记与本文档有关的偏移：

- 第 ② 段从「对账 + 三个抓取 + 对账后两步」缩成「对账 + 两个抓取」。
  `AFTER_RECONCILE` 整个阶段常量删除——它当初存在的唯一理由就是「等 reconcile
  释放 `/api` 配额」，没有这两步之后阶段本身没有意义。
- 第 2 节「各表的名额」里给 files 的 70 分钟不再占用窗口预算，窗口从 8.5 小时
  的实际需求回落；`--launch-hours` 的默认值未动，留待有实测再调。
- 少了两步之后，「同走 `/api` 配额所以要串行」这条约束在链上只剩
  `reconcile` 与 `fetch-sizes` / `fetch-readme` 的并行——它们本就分属不同端点。
