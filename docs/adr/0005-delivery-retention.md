# ADR-0005: 交付产物留存——清副本、留账

**日期**: 2026-11-17
**状态**: 已实施

---

## 背景

交付台账只增不删（ADR-0003）。台账里每条都带产物字节：query 型的 `data.parquet`
可能几十 MB，backfill 的 xlsx 也有几十 KB。目前 4 份需求、9 条交付还能接受；一旦有
`daily` 需求，一个月就是 30 份 × 几十 MB，而且**没有句点**。

但「清理」很容易走到反面：REQ-0004 那次事故的教训正是「为了目录干净，把证据删了」。
所以先明确产物在档案里的地位：

- **manifest** 是档案：记着产物的文件名、字节数、sha256，以及基于哪版底库、哪版口径、
  哪版代码。**不可删、不可改**。
- **README.md** 是同一份档案的人读面：记着怎么复现、逐列怎么来的。**不可删、不可改**。
- **产物字节**是「当时交出去的那份文件」的副本，可由前两者重算。它是唯一可以不在的
  东西——前提是「不在」这件事本身要留痕。

## 决策

### 1. 清理是可选的、显式的、可预演的

新增 `request prune [<id>] [--keep N] [--dry-run]`（默认 `--keep 1`，不写 id 则全部需求）。
它只删 `manifest.result.files` 点名的那些文件，**manifest / README 一份不动**。
当前有效那条（`deliveries/` 下最新的目录）永远不删，`--keep` 至少为 1——它是 `INDEX`
指向的「当前有效」，也是人最常打开的那份。

不在 `run-due` / `daily.ps1` 里自动跑：清理是不可逆的，不该由定时链替人做决定。

### 2. 清掉的每一样都记进 `deliveries/PRUNED.json`

```json
{
  "version": 1,
  "updated_at": "…",
  "pruned": {
    "20261117T173045": {
      "pruned_at": "…",
      "files": [{"name": "….xlsx", "bytes": 22911, "sha256": "…"}]
    }
  }
}
```

sha256 取自那条交付自己的 manifest。于是「这一条交了什么」仍然答得出来，只是要按
manifest 复现、而不是打开现成文件。

**先记账、再删字节**：反过来在两步之间崩溃，会留下「产物没了、也没人说是清理掉的」
——那正是这套机制要防的「看起来坏了」。清理中断时重跑 `request prune` 即可收敛。

### 3. 三个读者都要认得这件事

- `INDEX.md` 多一列「产物」：`✓` 或 `已清理`。
- `request compare` 碰上已清理的那条，报「按留存策略清理，只剩 sha256」而不是
  「找不到产物表格」——后者会让人以为交付坏了。
- 体检新增 `delivery_products`：盯**账实相符**（记录里的 sha256 与档案不一致、
  说清理了却还在、当前有效那条被列进清理清单）。产物没留存只记个数、报在通过的那一行
  ——它是可重算的副本，不是故障。REQ-0001..3（开发样例）的历史产物早被手工删过，
  实测就是「6 个产物未留存」，不该让体检因此长期发红。

### 4. 反查影响面：`request usage <词条|库列>`

改一个词条的定义（或淘汰一个库列）之前，最该先回答「谁会受影响」。新增只读命令
`request usage`，扫所有 spec，列出引用点（条件 / 排序 / 输出列 / 回填列）与各自最近
交付的版本。认得词条名、别名与库列名；查不到返回 1，脚本可用。

## 不采纳的方案

- **自动清理（交付后保留最近 N 条）**：清理不可逆，且「N 是多少」取决于这次交付给谁、
  对方还要不要旧版——那只有人知道。留成显式命令，`--dry-run` 先看清楚。
- **把旧产物挪进冷存目录（而不是删）**：需求目录要能整体拷走、克隆下来仍读得懂；
  引一个仓库外的冷存路径，等于把「自包含」换成「看机器」。真要留，复制出来自己存。
- **删掉整条交付目录（连同 manifest）**：那是把台账当货架。缺的从来不是「条目少」，
  而是「哪条算数」——INDEX 已经在回答后者。
- **把「产物未留存」判成体检故障**：早期交付的产物早就手工删过、重算即可；判红只会
  让这条告警长期有效，然后被忽略。

## 后果

- **`request compare` 与「打开旧产物」需要先复现**：manifest 里备着口径与底库指纹，
  按 README 的复现段重跑即可；这也意味着比对旧交付要先花一次交付的时间。
- **磁盘占用变成可管理的**：`request prune --keep 2` 之后，每条需求只剩最近两版的产物。
- **`PRUNED.json` 是引擎生成物**：不手改；它与 INDEX 一样会在下次 prune 时整份重写。
- **体检项从 3 个变 4 个**（`delivery_anchors` / `delivery_products` / `delivery_index` /
  `口径版本`），都只判已交付的需求。

## 回滚

- 去功能：删 `prune`、`pruned_facts` 与 CLI 入口；`PRUNED.json` 是普通文件，删掉不影响
  任何 manifest。
- 去体检项：删 `CHECKS` 里的 `delivery_products` 一行。
- 去索引列：`index_lines` 去掉「产物」一列；`INDEX` 是生成物，下次重写即恢复。
