# ADR-0009：合并「两次全站扫描」——评估后暂缓

- 状态：暂缓（保留方案，等触发条件）
- 日期：2026-11-21
- 决策者：作者

## 背景

ADR-0008 把日常链定成「串行头 `collect --full-scan` → `build` ‖ 并行段 `reconcile`」，
两处都是全站扫描。2026-11-21 的体积审计把它列为「每天全站抓两次」的问题项，
预估可省 0.85 GB 存储与每天 12–20 分钟。

审计拆账后发现，这两个预估都建立在错误的前提上，需要先把事实摆清再决定是否动手。

## 事实（2026-11-21 实测）

### 1. 两份数据 99.95% 相同

11-21 当天两个来源各 1,141 页：

| 指标 | 数值 |
|---|---|
| 交集 id | 1,140,886 |
| 其中逐字段相同 | **1,140,360（99.95%）** |
| 内容变了（相隔 19 分钟的正常漂移） | 526 |
| 仅 reconcile 有（新增） | 50 |
| 仅 lean 有（消失） | 6 |

### 2. 但重复落盘的问题已在 P1 解决

`f2ec8bb`（DECISIONS #165）让 `reconcile` 落盘前读当天已落分块的记录指纹，
只落「当天还没出现过相同内容」的记录。离线实测：1,140,936 条里只有 **576 条**
未见，落盘量降到 0.05%（约 0.1 MB / 天，原来是 165 MB / 天）。

**所以「合并两次扫描」的存储收益已经归零。** 剩下的收益只有墙钟时间。

### 3. 分页漂移并不存在

ADR-0008 让 `reconcile` 用 `createdAt`（不可变序）而不是 `lastModified`，理由是
「按易变字段排序翻页会漂移、漏检」。这条理由在 `--full-scan` 场景下**没有实测支撑**：

- `lean` 全站唯一 id **1,140,892**，`reconcile` **1,140,936**；
- 仅 lean 有 6 个、仅 reconcile 有 50 个——恰好等于 19 分钟内库的自然新增与消失。

若按 `lastModified` 序全站扫会漏掉几百个，`lean` 的唯一 id 数应显著少于
`reconcile`。实测差 44 个（0.004%），说明 HF 的 cursor 分页足够稳定，
`lastModified` 序的全站扫描并没有实质漏检。

## 可选的合并方案

### 方案 A：`reconcile` 不再扫描，从当天 raw 读 `seen`

`ReconcileSession.remember` 只取 `record["id"]` 与 `record.get("sha")`，
而 raw 分块里正有这两列。理论上 `seen` 完全可以从当天 raw 得出：

```
seen = { id: 该 id 在 written_at 最晚的那条记录的 sha }
```

代价与风险：
- 需要新增「当天 collect 是否完整」的判据（读 runs 台账的 `stopped_reason`），
  不完整则不判下架——这是现有铁律「没扫完不判」的平移；
- `ReconcileSession` 的游标 / 续跑机制整体作废，`reconcile --max-pages` 也要删；
- `doctor._reconcile_sessions` 靠「页数 + 记录数」拼会话判断完整性，需重写；
- **失去「手动单独跑对账」的能力**：没有当天 raw 时无从对账，只能先跑 collect。

改动面覆盖 `reconcile` / `session` / `collect` / `parsers` / `doctor` / `refresh`
六个模块，等于重写对账。

### 方案 B：只把 `collect --full-scan` 改成 `createdAt` 序

好处是让 raw 成为「稳定序全站枚举」，为方案 A 铺路。但：
- 事实 3 表明漂移不存在，改序换不到可测收益；
- `source` 由 `mode + sort` 派生，改序会让分块命名变成 `lean_createdAt`，
  `lineage` 指纹全部作废、迫使一次全量重建。

### 方案 C（已采纳）：维持两次扫描，第二份只落差异

即 P1 的现状。存储无浪费（0.05%），语义无变化，风险为零。

## 决策

**暂缓方案 A 与 B，维持方案 C。**

理由：
1. 存储收益已被 P1 吃掉，合并换不到空间；
2. 剩下的是每天省一次全站扫描（约 12–20 分钟墙钟、约 1,123 次请求）。而
   `refresh` 的窗口是 00:30–09:00，实测有 8.5 小时余量；日配额约 288,000 次，
   1,123 次占 0.4%。**两项都不构成瓶颈**；
3. 方案 A 的代价是把一个「独立可跑」的对账改成「依附于当天采集」，这是能力
   的净损失，不该为了省 15 分钟去换。

## 触发条件（届时重启评估）

任一条成立时再启动方案 A：

- 探测积压持续上升（`doctor` 的「顺延」长期高于 `PROBE_DAILY_LIMIT` 的两倍），
  且确认瓶颈在 API 配额而非自设上限；
- `refresh` 实际收工时间逼近 09:00 软边界（连续三天）；
- 上游把全站扫描的成本抬高（如单页记录数下降导致页数翻倍、或新增限速）。

## 若启动，实施要点

1. **完整性判据先行**：先加「当天 `collect` 的 run 台账 `stopped_reason == "end"`」
   的检查，不满足则不判下架（只写差异清单、不动状态）。这是不可协商的前提。
2. **`seen` 取最晚写入的那条**：同一 id 在当天多个分块里出现时，按 `written_at`
   取最后一条的 sha，与 Bronze 的胜负规则保持一致。
3. **保留一条逃生舱**：`reconcile --scan` 强制自扫，供 raw 异常时排障；
   默认不扫。删掉这个开关，等于把「对账」和「采集」绑成死结。
4. **`doctor` 的完整性判据同步改**：`_reconcile_sessions` 现在按页数拼会话，
   改成按「当天 raw 的唯一 id 数 vs 基线」比对。
