# 被拦下时怎么办

系统的拦截都会在错误信息里说清「哪里不对、怎么补」。照做即可，不要绕过。
下表按错误信息里的关键词索引。

| 错误里出现 | 含义 | 处置 |
| --- | --- | --- |
| `缺 method/METHOD.md` | 这份需求没有过程记录 | `request method <id>` 生成骨架，按第二节填写 |
| `还是未填的骨架` | 骨架里的 `<!-- 待填：` 没删 | 写完后删掉那行标记 |
| `缺 ## 步骤 一节` | 文档没写可复跑的步骤 | 补 `## 步骤`，写清「先跑什么、再跑什么」 |
| `脚本 X 未登记` | 新脚本没进索引 | `request method <id>` 重算；再补用途 |
| `指纹与索引不符` | 脚本改过但索引没同步 | 确认改动无误 → `request method <id>` → 在 METHOD.md 记一句改了什么 |
| `v{n} 已被 history/v{n}.yaml 占用` | 改了口径没升版本 | `version` 改成 n+1，重跑；`request diff` 核对差异 |
| `只得到 0 行，低于 min_rows` | 多半是口径写错 | `request show` 核对条件与词条；确属真实的空结果才调 `min_rows` 并说明理由 |
| `超过 max_rows` | 条件过宽，或把百万行倒给对方 | 收窄条件；确认要全量才调高上限 |
| `表头第 N 行没有 'URL' 列` | 表结构变了（换表 / header_row 错） | 用 `request input --add` 看字段差异，再改 `header_row` / `key_column` |
| `表里没有 'X' 列——spec 与表头对不上` | 声明了表里不存在的列 | 改列名、改成 `manual`，或删掉该规则 |
| `输入表不存在或不是文件` | `input/` 快照丢了或被改名 | 重新 `--source` 收一份；若换的是新版本，走 `request input --add` |
| `没有 sheet 'X'` | `fill.source.sheet` 写错 | 按报错里列出的现有 sheet 名改 |
| `两份交付形态不同` | 一份 query、一份 backfill | 无可比性；改为分别对比同类交付 |
| `没有交付 <时刻>` | 目录名写错 | 按报错列出的现有目录名重跑 |
| `上一次交付的 manifest 读不出来` | 档案损坏或被手改 | 先 `doctor`；不要修补，用 `request compare` 确认影响面后重交 |
| `未命中底库 N 条`（不是错误） | 对方表里有底库没收录的库 | 整行留空并在说明页点名；**不要编值**，也不要为了凑数改标识列 |

## 三条底线

1. **错误信息是结论，不是障碍**。`--force` 只解决「一次性需求想再交一份」，不解决任何校验失败。
2. **不修补档案**。`manifest.json` 与 `README.md` 由引擎写；手改之后的档案不再是证据。
3. **不为了过闸而改口径**。为了让行数落进区间而调 `min_rows`、为了让指纹匹配而重算索引
   却不说明理由，都是把闸门调歪，比被拦更糟。
